# Подбор оборудования по входящему письму — пилот

Отдельный сервис для сервера Timeweb `5.129.223.80`. Не меняет обработчик звонков,
категории, товары, цены, строки сделок и существующие workflows. Автоматической
отправки писем клиентам нет. Единственная предусмотренная запись — комментарий
с предварительным подбором в таймлайне исходной сделки.

## Реализовано

- Приём `POST /bitrix/email-pick`, подтверждение очереди через HTTP 202.
- Постоянная очередь SQLite и повтор чтения, если письмо ещё не привязалось к сделке.
- Только открытые сделки из почты в заданной воронке (`EMAIL`, категория `0` по умолчанию).
- Проверка отдельным REST-запросом полной привязки входящего письма к единственной сделке.
- Два AI-шага: выделение позиций с проверкой цитат, затем сравнение с карточками кандидатов.
- Поиск по CS-Cart API и повторное чтение конкретных карточек. Нет неявной подмены API YML-фидом.
- До 10 позиций, 3 запросов на позицию, 8 кандидатов на позицию и 30 полных карточек на письмо.
  Ограниченный поиск явно обозначается в результате; отсутствие кандидата не означает отсутствие в каталоге.
- Названия, цены, артикулы и ссылки берутся из каталога; AI не может добавить посторонний ID товара.
- Повторное чтение письма перед результатом/записью и остановка при изменении источника.
- Дедупликация запросов и писем. Таймаут записи переводит задание в `uncertain`, без слепого повтора.
- Секрет в заголовке `X-Webhook-Secret` или поле POST `secret`; секреты в URL не поддерживаются.
- Режим по умолчанию — `PICKER_WRITE_ENABLED=false`, результат доступен только по защищённому `/jobs/ID`.

Вложения, OCR, Excel/PDF и цитируемые старые цепочки отдельно не разбираются. Первая версия
всегда требует проверки менеджером. Модель может ошибиться при сравнении; положительный
автоматический вывод не разрешает добавлять товар в сделку или отправлять предложение.
Потребность извлекается из полного текста письма, поэтому старую переписку нужно проверять.

## Перед развёртыванием

Нужно подтвердить доступность сервера/runner, свободный порт 8091 и домен HTTPS.
Подключённые к ChatGPT коннекторы не предоставляют свои ключи этому сервису.
Потребуются отдельные серверные значения `BITRIX_WEBHOOK_URL`, `CSCART_API_EMAIL`,
`CSCART_API_KEY`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `PICKER_WEBHOOK_SECRET`.
Вебхук CRM должен читать сделки, активности и их привязки, читать/добавлять комментарии.
CS-Cart учётной записи достаточно чтения товаров и характеристик. Вводить секреты
следует в закрытой консоли сервера или защищённых Secrets, не в issue, README или публичные логи.

Текущий проект уже использует OpenAI для звонков; модель подбора задаётся явно,
без предположения о доступности конкретной версии у API-ключа.

## Установка на сервере

Из корня отдельной копии репозитория:

```bash
cp deploy/product-picker/.env.example deploy/product-picker/.env
chmod 600 deploy/product-picker/.env
# Заполнить секреты локальным редактором/хранилищем секретов.
python3 -m unittest discover -s product_picker/tests -v
docker compose -p kwatt-email-picker -f deploy/product-picker/compose.yml up -d --build
curl --fail http://127.0.0.1:8091/health
```

Сервис слушает только loopback сервера. SQLite хранится в отдельном Docker volume;
не запускать одновременно два экземпляра на одном томе. Не выполнять `down -v`.
Образ не устанавливает сторонние Python-пакеты и работает непривилегированным пользователем.

Подключить **существующий** HTTPS reverse proxy к `127.0.0.1:8091` после осмотра сервера.
Ограничить тело запроса 16 КБ; настроить rate limit. Не запускать второй proxy на занятых 80/443.
Установщик намеренно не меняет Nginx, Docker-сети, firewall или работающие контейнеры автоматически.

## Битрикс24 2.0

Рабочий маршрут: `Создана сделка → проверка источника EMAIL → Исходящий Вебхук`.
Основной анализ выполняет сервер, а результат возвращается в CRM REST-записью комментария;
обычный исходящий вебхук не следует считать синхронным возвратом текста в ноду AI-анализ.
Существующую заготовку AI-ноды необходимо отключить/удалить из публикуемого маршрута,
либо отдельно реализовать передачу подготовленных данных через поля CRM и второй триггер.

В webhook передавать JSON или form-urlencoded со следующими ключами:

```json
{"deal_id":"<ID сделки из данных триггера>","secret":"<секрет из защищённой настройки>"}
```

`activity_id` можно передать для обработки конкретного письма. Без него выбирается самое
новое входящее письмо, связанное со сделкой. При поздней привязке сервис повторяет чтение
с паузами, не запускает подбор по одному названию сделки. Повторный POST с теми же ID
возвращает то же задание. Новые письма существующей сделки требуют отдельного события
с явным `activity_id`: пилот не отслеживает их автоматически.

Не подставлять код поля ID наугад: выбрать значение из панели данных редактора.
Сохранить и проверить реальный формат запроса на одной тестовой сделке до публикации.

## Приёмка и включение записи

1. Оставить `PICKER_WRITE_ENABLED=false`.
2. Проверить подключения CRM/CS-Cart/модели и HTTPS.
3. На тестовых примерах проверить точную модель, запрос без модели, комплект против
   отдельного привода, неизвестные параметры и письмо с вложением.
4. Убедиться, что результаты `/jobs/ID` имеют `dry_run_done`, без изменений CRM.
5. После проверки изменить серверный режим на `true` и пересоздать только этот контейнер.
6. Запустить один пилотный подбор, подтвердить один комментарий и отсутствие дубля
   при повторном событии. Затем опубликовать шаблон 2.0 для выбранной воронки.

Для `uncertain` сначала вручную найти служебный маркер в таймлайне. Не удалять очередь
и не ставить повтор записи, пока не установлено, был ли комментарий сохранён.
Не логировать тела писем, секреты или результаты модели в публичный GitHub Actions.
Доступ к `/jobs/ID` содержит детали заявки: этот маршрут тоже требует секрета.

## Остановка

```bash
docker compose -p kwatt-email-picker -f deploy/product-picker/compose.yml stop
```

Остановка этого проекта не останавливает существующую обработку категорий/звонков.
Настроить резервное копирование и срок хранения SQLite перед постоянной эксплуатацией.
