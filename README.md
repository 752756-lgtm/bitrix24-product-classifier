# Bitrix24 Call Summarizer

Сервис принимает расшифровку входящего звонка, находит связанную сделку и автоматически:

1. делает короткое резюме разговора и добавляет его в таймлайн сделки;
2. заменяет название сделки на конкретную суть звонка;
3. если обсуждалась конкретная группа товаров, заполняет поля `Категория товаров (Сайт)` и `Подкатегория товаров (Сайт)`.

Категории загружаются из YML. Модель может выбрать только существующую в каталоге пару «категория → подкатегория». Если звонок не относится к определенной товарной группе, поля категории не изменяются.

## Поддерживаемые события

`POST /bitrix/call-transcript` принимает:

- JSON с `deal_id` и `transcript`;
- JSON/form-urlencoded с `activity_id` — сервис сам читает активность через `crm.activity.get`, берет `DESCRIPTION` и находит привязанную сделку;
- стандартные ключи события Битрикс24 `data[FIELDS][ID]`, `data[FIELDS][OWNER_ID]` и `data[FIELDS][DESCRIPTION]`.

Для старой сделки доступен `POST /bitrix/backfill-deal/{deal_id}`. Сервис получает все связанные дела типа «Звонок», начиная с последнего, и использует первую доступную готовую расшифровку через `crm.activity.call.getTranscript`.

Пример проверки без записи в CRM:

```bash
curl -X POST 'https://service.example.ru/bitrix/call-transcript?dry_run=true' \
  -H 'Content-Type: application/json' \
  -H 'X-Webhook-Secret: your-secret' \
  -d '{"deal_id":123,"transcript":"Клиенту нужен самоходный штабелер 1,5 тонны с высотой подъема 4,5 метра"}'
```

## Настройка

1. Скопируйте `.env.example` в `.env` и заполните значения.
2. Входящему вебхуку Битрикс24 выдайте права CRM на чтение активностей, чтение и изменение сделок, добавление комментариев таймлайна.
3. Укажите URL YML и ключ OpenAI API.
4. Настройте в Битрикс24 отправку события после появления расшифровки разговора на `/bitrix/call-transcript`.

Для стабильной работы рекомендуется указать постоянные коды пользовательских полей в `CATEGORY_FIELD_ID` и `SUBCATEGORY_FIELD_ID`. Если они не заданы, сервис ищет поля по названиям. Для полей-списков текстовые значения автоматически преобразуются в ID вариантов.

## Запуск через Docker

```bash
docker build -t bitrix24-call-summarizer .
docker run -d --restart unless-stopped --env-file .env -p 8080:8080 bitrix24-call-summarizer
```

Проверка:

```bash
curl http://localhost:8080/health
```

Проверка старой сделки без записи:

```bash
python -m classifier.backfill --deal-id 123456
```

Запись подтвержденного результата:

```bash
python -m classifier.backfill --deal-id 123456 --write
```

## Постоянная обработка категорий за 2025 год

Worker продолжает согласованный план из 5 617 сделок независимо от сессии чата. Он работает последовательно, пачками по 20 записей, и выдерживает не менее 60 секунд между пачками записи. Единственный writer запускается последовательными GitHub-hosted job; production deploy обслуживает только веб-сервис и удаляет legacy-контейнеры category-worker, не затрагивая их SQLite-данные.

Безопасность обработки:

- исходный план хранится в репозитории только как HMAC-отпечатки — без ID, названий и комментариев сделок;
- план криптографически привязан к порталу и исходному источнику решения: названию сделки, товарным строкам либо точному сочетанию стандартных полей сделки `TITLE` + `COMMENTS`; изменение источника блокирует устаревшую запись;
- перед каждой записью повторно проверяются этап, категория и подкатегория;
- ручная правка переводит строку в `conflict` и не перезаписывается;
- этапы «Дубль», «Реклама / Спам», «Поставщик», «Документы / Акты» и «Доставка» пропускаются во всех воронках;
- после таймаута сначала проверяется фактическое состояние сделки, и только затем решается вопрос о повторе;
- прогресс текущего job после каждой пачки сохраняется в SQLite WAL, а между job авторитетным checkpoint служит проверенное live-состояние CRM;
- лимиты Bitrix24 включают сохраняемую экспоненциальную паузу до 15 минут;
- ограниченная цепочка продолжений и ежечасный scheduled recovery восстанавливают обработку после обрыва runner.

Режим `deal_text` относится только к стандартному полю сделки `COMMENTS`: timeline-комментарии, письма CRM activity и сообщения открытых линий в этот источник не входят. Перед записью worker запрашивает `TITLE`, `COMMENTS`, этап и оба поля классификации одним свежим REST-снимком и сверяет его с HMAC fail-closed. Bitrix24 не предоставляет compare-and-swap, поэтому остаётся короткое неизбежное окно между этим финальным чтением и немедленным `crm.deal.update`; автоматический откат после конкурентной правки не выполняется, чтобы не затереть ручные изменения.

Протокол allowlist v4 также поддерживает операции `category_*`, которые изменяют только поле категории. Исходная подкатегория входит в подписанный переход и отдельный HMAC guard, поэтому её изменение обнаруживается как `conflict` даже при новом полном сканировании; пустые и legacy-значения не заменяются и не добавляются в публичную таксономию. Целевая категория всё равно обязана быть существующим и проверенным вариантом live enum.

Протокол allowlist v5 добавляет режимы `activities` и `category_activities` для решений по входящим письмам и готовым расшифровкам звонков. В репозиторий попадают только HMAC полного индекса activities и HMAC-локаторы выбранных источников: ID activities, темы, тела писем и расшифровки не сохраняются. Лёгкий initial scan не читает activity evidence. Непосредственно перед записью worker обрабатывает не более пяти activity-строк, получает keyset-индексы A/B через deal binding, между ними загружает только подписанные источники, затем одним batched-проходом ещё раз сверяет индекс и требует точного совпадения raw evidence, этапа и исходных полей сделки.

GitHub-hosted fallback использует CRM как авторитетное постоянное состояние: каждый новый job заново сверяет все сделки и пропускает уже подтверждённые, исключённые либо вручную изменённые строки. Job работает до 310 минут, затем сам запускает продолжение; ежечасное расписание страхует аварийный обрыв и не прерывает активный job. После терминального результата создаётся технический tag, привязанный к хэшу worker и плана, поэтому последующие проверки завершаются без обращения к CRM.

Для GitHub-hosted продолжений можно отдельно настроить стабильный secret `PRECISION_PLAN_KEY`, использованный при подписи allowlist; без него URL вебхука нельзя ротировать до завершения текущего плана.

Агрегированное состояние без ID и названий сделок публикуется в job summary workflow `Backfill Bitrix24 categories for 2025`; полный worker log остаётся только во временном каталоге runner и не выгружается.

Ручная read-only проверка конфигурации:

```bash
python -m classifier.precision_worker --check-config \
  --state /tmp/precision-check.sqlite3 \
  --status /tmp/precision-check-status.json
```

## Развёртывание через GitHub Actions

Workflow `.github/workflows/deploy.yml` запускается вручную на production self-hosted runner. Он:

1. проверяет конфигурацию и секреты;
2. запускает тесты и собирает Docker-образ на production runner;
3. выполняет обязательный dry-run одной сделки без записи;
4. останавливает и удаляет legacy-контейнеры category-worker, оставляя их данные на диске;
5. разворачивает только веб-сервис с health check, crash guard и rollback.

Один раз добавьте в `Settings → Secrets and variables → Actions` следующие Repository secrets:

| Secret | Значение |
|---|---|
| `BITRIX_WEBHOOK_URL` | базовый URL входящего вебхука Битрикс24 |
| `PRECISION_PLAN_KEY` | необязательный стабильный секрет, которым подписан годовой allowlist |
| `OPENAI_API_KEY` | ключ OpenAI API |
| `WEBHOOK_SECRET` | отдельная длинная случайная строка для защиты HTTP endpoint |

Для ручного запуска откройте `Actions → Deploy call summarizer → Run workflow` и укажите ID сделки для обязательного dry-run. Dry-run не меняет CRM; production deploy разрешён только после completion tag годового плана.

Workflow `.github/workflows/precision-backfill-2025.yml` автоматически запускается при изменении worker или подписанного плана в `main`, а также может быть запущен вручную только из `main`. Он требует только `BITRIX_WEBHOOK_URL`. Первый safety gate отменяет и удаляет конкретный старый queued deploy лишь после доказательства, что ни runner, ни один шаг не запускались; hosted workflow после этого остаётся единственным category-writer.

Если старый deploy всё же успел завершиться до safety gate, workflow сначала ставит возобновляемый retirement-marker, подтверждает доступность Docker и удаляет legacy category-worker на production runner. Только после отдельного retired-marker запускается hosted writer, который безопасно продолжает план по live-состоянию CRM.

Сервис публикуется только на `127.0.0.1:8080`. Для приема событий Битрикс24 нужен HTTPS reverse proxy; его следует включать отдельно после успешного dry-run.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `BITRIX_WEBHOOK_URL` | Базовый URL входящего вебхука Битрикс24 |
| `OPENAI_API_KEY` | Ключ OpenAI API |
| `OPENAI_MODEL` | Модель анализа, по умолчанию `gpt-5.6-luna` |
| `YML_URL` | URL YML-фида с деревом категорий |
| `CATEGORY_FIELD_NAME` | Название поля категории |
| `SUBCATEGORY_FIELD_NAME` | Название поля подкатегории |
| `CATEGORY_FIELD_ID` | Постоянный код поля категории (`UF_CRM_...`) |
| `SUBCATEGORY_FIELD_ID` | Постоянный код поля подкатегории (`UF_CRM_...`) |
| `WEBHOOK_SECRET` | Секрет, ожидаемый в заголовке `X-Webhook-Secret` |
| `HTTP_TIMEOUT` | Таймаут внешних запросов |
| `TITLE_MAX_LENGTH` | Максимальная длина названия сделки |
| `PRECISION_YEAR` | Год постоянной обработки, сейчас `2025` |
| `PRECISION_BATCH_SIZE` | Сделок в одной пачке записи, сейчас `20` |
| `PRECISION_WRITE_INTERVAL_SECONDS` | Минимальный интервал между пачками записи |
| `PRECISION_API_INTERVAL_SECONDS` | Общий интервал между REST-вызовами worker |
| `PRECISION_HTTP_TIMEOUT` | Таймаут REST-вызовов worker |
| `PRECISION_STATE_PATH` | Путь к постоянной SQLite |
| `PRECISION_STATUS_PATH` | Путь к краткому JSON-статусу |
| `PRECISION_PLAN_KEY_PATH` | Путь к постоянному закрытому ключу согласованного плана |
